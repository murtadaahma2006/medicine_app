# قواعد ذهبية لترحيلات قاعدة البيانات (Migration Rules)

> وثيقة دائمة — تُراجع قبل أي تعديل على المخطط. مصدرها: مراجعة مهندس البيانات عند إغلاق المرحلة الثانية.

## القاعدة 1: أي تغيير مخطط بعد أول إصدار = dbVersion++ + migration صريح
- زد `databaseVersion` في database_helper.dart وأضف منطق الترحيل في `_onUpgrade`.
- ⛔ **لا تعدّل `onCreate` أبداً بدعوى "تحديث المخطط"** — المستخدم القديم لا يمرّ بـ onCreate أصلاً، وتعديله وحده يعني انهيار التطبيق عنده.
- `onCreate` الجديد يجب أن ينتج نفس مخطط (v1 + كل الترحيلات) حتى يكون الإصداران متطابقين للمستخدم الجديد.

## القاعدة 2: SQLite لا يدعم ALTER TABLE ADD CONSTRAINT
- إضافة FK جديد (مثل corrections.drill_id → drills) تتطلب **إعادة بناء الجدول**: إنشاء جدول جديد بنفس البيانات → نسخ الصفوف → تبديل الأسماء داخل transaction.
- خطّط لها كمهمة migration مستقلة بذاتها منذ البداية، لا كتعديل جانبي.

## القاعدة 3: فخ REPLACE + foreign_keys
- `ConflictAlgorithm.replace` في SQLite هو فعلياً DELETE+INSERT؛ ومع تفعيل foreign_keys فإن أي صف تابع عبر CASCADE **يُمحى صامتاً** عند كل "إعادة إدراج" للأب.
- لهذا: `insertLesson` تستخدم INSERT OR IGNORE، والفخ موثّق بتعليق فوق الدالة مباشرة. لا تعد إليه.

## القاعدة 4: أداء البحث
- فهرس idx_vocabulary_search مع نمط `'term%'` يكفي لعشرات آلاف الكلمات.
- ⏸️ FTS5 مؤجَّل — لا يُقدَّم إلا عند وجود مشكلة أداء حقيقية مقاسة.

## حالة النسخة الحالية
- databaseVersion = 1 · لا ترحيلات بعد · FK مفعّل عبر PRAGMA في onConfigure.
- المرجع المؤجَّل: corrections.drill_id → جدول drills (المرحلة الثالثة) — راجع القاعدة 2 عند تنفيذه.
